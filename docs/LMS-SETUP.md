# Student portal — setup

About 15 minutes, once. After this the NGO never touches the database again:
teachers approve teachers, teachers admit students.

---

## 1. Create the Supabase project

1. Sign up at [supabase.com](https://supabase.com) (free tier is enough).
2. **New project** → name it `umeed-o-shakhur`. Choose the region closest to
   Pakistan (Singapore or Frankfurt).
3. Save the database password somewhere safe. You will not need it day to day.

## 2. Create the tables

Dashboard → **SQL Editor** → **New query**. Paste the whole of
[`supabase/schema.sql`](../supabase/schema.sql), then **Run**.

You should see "Success. No rows returned." Re-running it later is safe — it is
written to be idempotent, so applying an updated version does not lose data.

## 3. Turn off public signups

**This step is what stops strangers creating accounts.** Without it, anyone
could register directly against Supabase and bypass both gates.

Dashboard → **Authentication** → **Sign In / Providers** → **Email**:

- **Allow new users to sign up** → **off**
- **Confirm email** → off (accounts are created already-confirmed by our
  server, which is what the join code and approval code are for)

Turning signups off does *not* stop people signing in, and it does not stop our
own server routes creating accounts — those use the service-role key, which is
allowed to. It only closes the public door.

## 4. Copy the keys

Dashboard → **Project Settings** → **API**. You need three values:

| Supabase field | Environment variable | Secret? |
| --- | --- | --- |
| Project URL | `NEXT_PUBLIC_SUPABASE_URL` | no |
| `anon` `public` key | `NEXT_PUBLIC_SUPABASE_ANON_KEY` | no |
| `service_role` key | `SUPABASE_SERVICE_ROLE_KEY` | **yes — treat like a password** |

The anon key is safe in the browser because every table has Row Level Security
enabled and denies by default. **The service-role key bypasses all of it.** It
belongs only in server environment variables. If it is ever committed, pasted
into a chat, or shared, rotate it immediately (same page → **Reset**).

## 5. Set up approval emails

Teacher approval codes are emailed to the NGO office, so you need a sender.

1. Sign up at [resend.com](https://resend.com) (free tier: 3,000 emails/month —
   this uses a handful a year).
2. Verify your domain, or use their `onboarding@resend.dev` sender for testing.
3. Create an API key.

Then set:

- `NGO_APPROVAL_EMAIL` — the inbox that receives approval codes. **Whoever
  reads this inbox decides who becomes a teacher**, so use an address a
  responsible person actually watches.
- `RESEND_API_KEY`
- `RESEND_FROM_EMAIL` — e.g. `portal@umeedoshakhur.org`

## 6. Put the variables in place

**Locally** — copy `.env.example` to `.env.local` and fill it in.

**On Netlify** — Site settings → **Environment variables** → add all six.
Redeploy after saving; environment variables are read at build and run time.

## 7. First run

1. Go to `/lms/signup/teacher` and request access for yourself.
2. The approval code arrives in the `NGO_APPROVAL_EMAIL` inbox. Enter it.
3. You now have a teacher account. Open the teacher console, create a class,
   and read the join code out to your students.

---

## How the two gates work

**Students** join with a **class code** — six characters, generated by a
teacher, read aloud at camp. Codes can carry a seat limit and an expiry, and a
teacher can issue a new one at any time (which instantly kills the old one).

**Teachers** cannot approve themselves. Requesting access sends a code to the
NGO office, *never to the applicant*. Someone at the office has to recognise
the name and pass it on. The automation is just the delivery; the actual
decision is a human one.

## What is enforced, and where

| Control | Where it lives |
| --- | --- |
| Role can never be chosen by the user | Set server-side in `app/api/auth/*`; the student route has no code path that produces a teacher |
| Role can never be changed afterwards | Database trigger `profiles_role_immutable` — fires even for the service role |
| Students see only their own classes' content | Row Level Security policies, not application code |
| Students cannot read join codes | `classes` is teacher-only at the policy level |
| Codes cannot be brute-forced | Hashed at rest, compared in constant time, attempt-capped, rate-limited per IP and per email |
| A leaked service key is the only single point of failure | Which is why step 4 matters |

Row Level Security is the real boundary. The login redirect in `middleware.js`
is a convenience — even with it removed entirely, a signed-out browser could
not read a single row.

## Honest limits

**A class code is a shared secret.** If a student forwards it, whoever has it
can create a student account in that class until the code is changed. This is
the same tradeoff Google Classroom makes, and it is the price of self-service
signup without a roster. Mitigations, in order of effectiveness:

- Set a **seat limit** matching your expected intake — the code dies when full.
- Set an **expiry** of a few days around the camp.
- **Change the code** once everyone has joined (one click).

A student account can only ever read that class's announcements, assignments,
and links. There is no personal data of other students exposed, and no way to
escalate to teacher.

**The teacher gate is only as careful as the person reading the inbox.** If
they hand out codes without checking who is asking, the gate is open. Make sure
whoever watches that inbox knows they are the check.

**Passwords are the weak point, as always.** The floor is 8 characters. If
students set up accounts on shared phones, remind them to sign out.

## Day-to-day

| Task | Who | How |
| --- | --- | --- |
| Add a teacher | NGO office | They request at `/lms/signup/teacher`; office passes on the code |
| Add students | Teacher | Create a class, read out the code |
| Stop new joins | Teacher | "Close" the class, or change the code |
| Post an announcement / assignment / book | Teacher | Teacher console |
| Remove someone | NGO office | Supabase → Authentication → Users → delete |

Removing a user is the one thing with no in-app button. It is rare, and
deleting the auth user cascades to their profile and class membership
automatically.
